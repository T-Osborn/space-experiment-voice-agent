# 旧会话版本循环修复

日期：2026-10-15。修复代码版本：`2.0.0-dev.2`。这是任务会话升级交互修复，没有改变科学参数、实验步骤或异常恢复权限，也没有发布2.0下载包。

## 已确认原因

T反馈“开始流程”后反复提示不一致、重新选择。只读检查当前页面，实际可见“流程版本不一致，已暂停”；进度面板却提示“说恢复流程回到原步骤”。没有替用户点击、录音或重新开始。

程序复现发现，持久化旧任务的`procedure_version`与当前流程版本不一致。同一实验的重新选择只更新选择提示，不重建任务，旧流程版本仍在；随后“开始流程”再次触发版本保护。保护本身应保留，但原提示“重新选择并开始流程”不能解除这种状态，因此形成循环。进度面板还可能沿用旧的普通暂停原因，给出错误的恢复建议。

## 本轮修复

旧任务直接说“开始流程”时，改为说明版本差异、保留旧记录，并请求单独确认重新开始。用户明确说“确认重新开始”之前，不清空读数、不沿用旧确认、不推进步骤。同一实验重新选择时也明确告知需要建立新任务，不再提示重复选择后开始。

版本不一致采用独立暂停原因。语音提示与界面下一步均指向“重新开始”及单独确认，不将它当成普通操作者暂停。知识查询仍可执行，且不改动实验记录。更换流程标识也不能绕过版本保护。

确认建立新任务后，旧任务作为历史记录归档，新任务使用当前版本从第1步开始。导出记录的`procedure.version`保留旧会话版本，`loaded_version`记录当时加载版本，避免把旧记录误标为新版。现有原始口述值、异常、未解决冲突和日志保留在旧记录中，不等于把异常解除后继续原实验。

取消或普通的“确认无误”都不会替代这次任务变更确认。数据库写入和重试继续沿用原有事务与回执机制，避免一次确认产生多份归档。

## 当前服务与临时操作

没有自动停止`http://127.0.0.1:8100/`的运行进程，也没有读取其密钥、清理Cookie或修改用户数据库。已运行的`2.0.0-dev.1`服务不会因文件修改自动加载新代码；完整修复需重新启动后生效。

旧服务已有可用的显式新建任务路径。用户可先说“重新开始”，等归档说明后再说“确认重新开始”。本轮在隔离的旧版本模拟会话中验证这两句能回到当前流程第1步，旧口述值保留在归档内。这只是演示任务重建，不是让已暂停的真实实验自动恢复。后续T已明确反馈19步语音测试均无问题，说明这条现有新建任务路径能够继续测试；归档文件内容未独立核验。
